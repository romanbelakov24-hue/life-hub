# life hub

Личный трекер расходов и учебный планер в одном интерфейсе. Данные лежат в базе
(Turso / libSQL), а не в браузере, — сайт открывается с телефона и с ноутбука с
одними и теми же записями.

**Стек:** Next.js 15 (App Router) · TypeScript · Turso (libSQL) · Tailwind CSS 4 ·
Recharts · lucide-react.

---

## Быстрый старт

```bash
npm install
```

Дальше — два варианта.

### Вариант А: локально, без Turso

Ничего настраивать не нужно. Если переменные окружения не заданы, приложение
само создаёт файл `local.db` в корне проекта:

```bash
npm run dev
```

Открыть <http://localhost:3000>. Годится, чтобы попробовать интерфейс, но данные
останутся только на этом компьютере.

### Вариант Б: с Turso (нужен для доступа с телефона и деплоя)

База заводится либо через веб-панель <https://app.turso.tech> (создать базу,
скопировать URL, выпустить токен — CLI не нужен), либо через терминал.

Через CLI:

```bash
npm install -g turso
```

```bash
turso auth login
```

```bash
turso db create life-hub
```

Адрес базы и токен:

```bash
turso db show life-hub --url
```

```bash
turso db tokens create life-hub
```

Дальше — файл `.env.local` в корне проекта (шаблон — в `.env.example`):

```
TURSO_DATABASE_URL=libsql://life-hub-<твой-аккаунт>.turso.io
TURSO_AUTH_TOKEN=<токен>
```

Создать таблицы и запустить:

```bash
npm run db:migrate
```

```bash
npm run dev
```

## Демо-данные

Чтобы посмотреть, как выглядят графики и списки на реальных объёмах, можно
залить примерные траты за два месяца, расписание, задачи и заметки:

```bash
npm run db:seed -- --yes
```

Флаг `--yes` обязателен: скрипт пишет в ту же базу, что и приложение. Чтобы
стереть локальные демо-данные, достаточно удалить файл `local.db`.

## Деплой на Netlify

1. Залить проект в репозиторий на GitHub.
2. На netlify.com → **Add new site → Import an existing project** → выбрать
   репозиторий. Команда сборки и папка публикации уже заданы в `netlify.toml`,
   менять их не нужно. Плагин `@netlify/plugin-nextjs` подключается сам.
3. **Site configuration → Environment variables** → добавить
   `TURSO_DATABASE_URL` и `TURSO_AUTH_TOKEN` (значения из панели Turso).
4. Deploy. Схема создаётся автоматически при первом запросе, отдельный шаг
   миграции не нужен.

Если переменные добавлены уже после первой сборки, нужен повторный деплой:
**Deploys → Trigger deploy → Deploy site**. Переменные читаются в момент
выполнения, но собранный сайт без них просто не запустится.

**После того как сайт открылся хотя бы раз** и таблицы точно созданы, можно
добавить ещё одну переменную — `SKIP_SCHEMA_INIT=true`. На личном сайте с
одним пользователем функция почти всегда стартует холодной, и без этой
переменной каждое такое открытие сначала ждёт ответа на CREATE TABLE и только
потом запускает настоящие запросы страницы; переменная убирает этот лишний
круг до базы. Добавлять раньше первого успешного запуска нельзя — см.
`.env.example`.

Проект так же собирается и на Vercel — там шаги те же, `netlify.toml` просто
игнорируется.

### Почему переменные обязательны

Без `TURSO_DATABASE_URL` продакшн-сборка не переключается на локальный файл,
а падает с понятной ошибкой. Это сделано намеренно: на серверлес-хостинге
файловая система эфемерна и доступна только для чтения, поэтому молчаливый
откат дал бы сайт, который выглядит рабочим, но теряет каждую запись.

### Про доступ

Авторизации в приложении нет — это личный сайт, и единственное, что защищает
данные, это неизвестность адреса. Если так не устраивает: у Netlify есть защита
сайта паролем (**Site configuration → Access & security → Visitor access**,
доступность зависит от тарифа), либо в проект добавляется собственная страница
входа.

## Структура проекта

```
netlify.toml                 # команда сборки и версия Node для Netlify
src/
├── app/                     # маршруты (App Router)
│   ├── page.tsx             #   /          — обзор
│   ├── expenses/page.tsx    #   /expenses  — расходы (журнал + аналитика)
│   ├── schedule/page.tsx    #   /schedule  — расписание
│   ├── tasks/page.tsx       #   /tasks     — задачи
│   ├── notes/page.tsx       #   /notes     — заметки
│   ├── globals.css          #   дизайн-токены и базовые стили
│   ├── error.tsx            #   экран ошибки (чаще всего — нет связи с базой)
│   └── layout.tsx           #   шрифты, тема, каркас приложения
│
├── components/
│   ├── layout/              # сайдбар, нижний таб-бар, шапка, переключатель темы
│   ├── ui/                  # базовые примитивы: панель, кнопка, поля, модалка
│   ├── charts/              # общее для графиков: тема и тултип
│   ├── expenses/            # виджеты раздела расходов
│   ├── study/               # расписание, задачи, заметки
│   └── overview/            # карточки стартовой страницы
│
├── config/                  # то, что чаще всего хочется поменять
│   ├── nav.ts               #   пункты навигации
│   ├── schedule.ts          #   учебные дни, число пар, расписание звонков
│   ├── palette.ts           #   цвета категорий и предметов
│   └── icons.ts             #   иконки категорий
│
└── lib/
    ├── types.ts             # доменные типы — одна точка правды
    ├── db/                  # подключение к Turso, DDL-схема, чтение строк
    ├── queries/             # выборки из базы (только SQL, без логики)
    ├── actions/             # серверные действия: создание, правка, удаление
    ├── analytics/           # чистые функции: агрегация трат, матрица задач
    └── utils/               # даты, форматирование, разбор быстрого ввода
```

### Как это устроено

**Слои данных.** `queries/` только читает из базы, `analytics/` только считает
над уже загруженными массивами, `actions/` только пишет. Страницы остаются
тонкими: получили данные — отдали в компоненты. Если нужно поменять формулу
среднего чека, правится один файл в `analytics/`, SQL трогать не приходится.

**Серверные действия вместо API-роутов.** Все изменения идут через функции с
`"use server"` в `lib/actions/`. Они валидируют вход, пишут в базу и вызывают
`revalidatePath`, после чего серверные страницы перечитывают данные сами —
отдельного слоя fetch на клиенте нет.

**Ошибки не бросаются наружу.** Действие всегда возвращает
`{ ok: true, data }` либо `{ ok: false, error }`, и компонент показывает текст
ошибки рядом с формой (см. `lib/actions/types.ts`).

**Состояние страницы в URL, состояние виджета — в компоненте.** Месяц и вид на
странице расходов лежат в `?month=&view=` (ссылку можно сохранить, кнопка
«назад» работает), а переключатель «список ↔ матрица» на задачах — обычный
`useState`, потому что это взгляд на те же данные, а не отдельная страница.

## Как вносить изменения

| Что нужно | Куда смотреть |
|---|---|
| Добавить раздел в меню | `src/config/nav.ts` + новая папка в `src/app/` |
| Изменить цвета или тему | блоки `:root` и `.dark` в `src/app/globals.css` |
| Другое расписание звонков, шестидневка | `src/config/schedule.ts` |
| Новые иконки категорий | `src/config/icons.ts` |
| Подсказки для быстрого ввода трат | `KEYWORD_HINTS` в `src/lib/utils/quick-parse.ts` |
| Новое поле в таблице | `src/lib/db/schema.ts` → `ALTER_STATEMENTS`, затем типы в `src/lib/types.ts`, запрос и действие |
| Новая метрика в статистике | `src/lib/analytics/expenses.ts` |

Схема базы эволюционирует так: новая таблица — в `SCHEMA_STATEMENTS`, новая
колонка — в `ALTER_STATEMENTS`, затем `npm run db:migrate`. Повторный запуск
безопасен: `CREATE TABLE IF NOT EXISTS`, а ошибки «duplicate column name»
скрипт игнорирует.

## Дизайн

Оформление собрано вокруг «бумажной» метафоры: тёплый фон, разделители
волосяными линиями вместо теней, крупные моноширинные цифры и один акцентный
цвет — вермилион. Заголовки набраны Unbounded, интерфейсный текст — Inter,
все числа — JetBrains Mono (моноширинные, поэтому колонки сумм не «прыгают»).

Тема переключается вручную (светлая / тёмная) или следует настройке устройства.
Цветовые пары проверены на контраст не ниже 4.5:1, цели касания — от 44px,
нижняя навигация учитывает безопасную зону экрана телефона.
